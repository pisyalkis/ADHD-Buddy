# Баги и риски

## 2026-08-26

- Последовательный проход по задачам (`walk_tasks_start` → `_walk_to_step`, bot.py:4630-4695) ставит `ctx.user_data["task_walk"] = True`, но если в пуле дел уже что-то есть, `_offer_task_input` показывает клавиатуру с кнопками `pool_use_item`/`pool_write_own` (bot.py:4971-4981, 4772-4781) — обе первым делом вызывают `clear_awaiting_flags(ctx, update)`, который безусловно удаляет `task_walk` (bot.py:5350) ещё до того, как `apply_task_edit` (bot.py:4961) успевает его проверить. В результате проход "по одной" молча обрывается на первом же шаге, где пул не пуст (частый случай), и пользователя вместо следующего слота возвращает на полный список задач.
- `apply_task_edit` (bot.py:4912-4969) снимает отметку "выполнено" с задачи при любом повторном сохранении слота, даже если новый текст совпадает со старым — `was_filled` проверяет только факт непустоты, а не изменение текста, хотя комментарий рядом (bot.py:4949-4951) описывает намерение снимать отметку именно при *смене* текста. Повторное сохранение того же текста (например через "✏️ Поменять" без реальной правки) откатывает уже выполненную задачу обратно в невыполненную.
- `finish_morning`/`_build_pinned_tasks_text` (bot.py:2298, 2503): `g(user['gender'], 'записано', 'записана')` согласует причастие с полом пользователя, а не с родом существительного "Утро" (средний род, всегда "записано"). Пользовательницы (gender='F') видят "✅ *Утро записана!*" — грамматическая ошибка, дублирующаяся теперь в двух местах (обычный текст сообщения и билдер закреплённого сообщения с зачёркиванием). Fallback-ветка при исключении использует правильный инвариантный текст "Утро записано!", что подтверждает: основной путь сломан, это не осознанный выбор.
- `personalize("😵 Отвлёкся(ась)", gender)` (bot.py:3561) не работает ни для одного пользователя: словарь неправильных форм `_PERSONALIZE_IRREGULAR` (bot.py:1027-1034) хранит ключ в нижнем регистре `"отвлёкся(ась)"`, а текст кнопки — с заглавной "Отвлёкся(ась)"; `str.replace` регистрозависим, общий regex-фоллбэк тоже не подходит (ждёт `(ла)`/`(а)`, а не `(ась)`). Кнопка коуча всегда показывает неперсонализированный текст "😵 Отвлёкся(ась)" для всех полов.
- `create_promo_code` (bot.py:636-645) делает `INSERT OR REPLACE`, который безусловно обнуляет `uses` при повторном создании кода с тем же именем, хотя история использований в `promo_redemptions` не удаляется, а лимит в `redeem_promo_code` проверяется только по счётчику `uses`. Если админ пересоздаёт уже использованный лимитированный промокод (например, чтобы поправить лейбл), лимит редемпшенов эффективно снимается и открывается заново.
- `check_notifications` (bot.py:7353-7381): `tz`, `now_dt`, `now`, `is_monday` и `day_key` вычисляются из `user`, взятого из общего снимка `get_all_notif_users()` в начале тика — и только *после* этого код перечитывает `user = get_user(uid)` свежим, чтобы закрыть уже известный баг с устаревшим `notif_enabled` (см. комментарий 16-го чекапа рядом). Однако сам часовой пояс и производные от него значения времени/даты выше по коду так и остаются вычисленными по старому снимку. Если пользователь меняет город/таймзону в тот момент, когда тик как раз перебирает пользователей, для этого тика могут сработать утренние/дневные/вечерние/недельные проверки по неверному локальному времени и календарной дате.
- `send_due_reminders` (bot.py:5205-5224): `rem` берётся один раз до `await app.bot.send_message(...)`; если пользователь успевает отредактировать это же напоминание (текст/время/повтор) во время этого `await`, последующий `reschedule_reminder`/`cancel_reminder` всё равно использует старые `rem["recur"]`/`rem["remind_at"]`, затирая только что сделанную правку — например, отключение повтора прямо в момент срабатывания не помешает напоминанию снова перепланироваться как повторяющееся.
- `_edit_or_send` (bot.py:1363-1373) — новый общий хелпер для "12 разделов бота теперь редактируют то же сообщение вместо нового" (#146): ловит вообще любое исключение из `q.message.edit_text(...)` и на любой ошибке шлёт `reply_text` тем же текстом как новое сообщение. Telegram Bot API кидает `BadRequest: Message is not modified`, когда текст и клавиатура совпадают с уже показанными — а это ровно то, что происходит при повторном/двойном тапе по одной и той же кнопке статичного экрана (🤖 Коуч, ℹ️ О боте, 🔒 Приватность, 🧠 Навыки, ⏰ Напоминания, 🗂 Карточка дня, 🍅 Фокус-режим, 💬 Обратная связь, 💎 Подписка, 🆕 Что нового, буддi, вкладки ⚙️ Общие и т.д. — все они теперь используют `_edit_or_send`, bot.py: строки со звонками ~3794, 3829, 3926, 3934, 4104, 4279, 4289, 4869, 5415, 5604, 6028, 6425, 6477, 6479, 6527, 6576, 6914). Двойной тап (а импульсивный повторный тап — типичное поведение именно для аудитории СДВГ, на которую рассчитан бот) не различается как "то же самое", падает в `except`, и вместо no-op редактирования уходит дублирующее новое сообщение — то есть именно тот чат-спам, который вся эта серия коммитов должна была устранить, тут же возвращается для самого частого сценария. `go_tab` (bot.py:5670-5684) содержит отдельную неразделяемую копию того же самого паттерна `try: edit_text / except: reply_text` — тот же баг, но фикс в `_edit_or_send` его не затронет, пока копия не приведена к общей функции.

Это отдельный сценарий от уже задокументированного бага `_edit_msg_or_send` (там — одно сообщение длиннее 4096 и зависший диалог, а не порча разметки при принудительной нарезке на несколько сообщений).

- `finish_morning` (bot.py:3106-3131) хранит мёртвый код: `changed_keys = {k for k in TASK_KEYS if task_fields[k] != existing.get(k, "")}` (3126) призван, по соседнему комментарию, "сбрасывать отметки выполнено только для полей, текст которых реально поменялся" — но `task_fields = _merged_task_fields(ctx, existing)` (3112), а `_merged_task_fields` (3060-3076) по собственному докстрингу теперь буквально возвращает `{key: existing.get(key, "") for key in TASK_KEYS}`, то есть построена из того же `existing`, с которым её потом сравнивают. `changed_keys` гарантированно всегда пустой набор — рудимент до рефакторинга (когда задачи ещё ставились через шаги ритуала M_FOCUS/M_B1/...), который сейчас ничего не делает, а его комментарий вводит в заблуждение о реальном поведении.

Метка с `*`, `_` или `` ` `` в аргументах команды либо ломает форматирование, либо валит `reply_text` с `BadRequest: Can't parse entities` — админ не получает подтверждения о создании кода.
- `grant30_callback` (bot.py:7710-7726, кнопка "🎁 +30" в /users) вызывает `_grant_and_notify` без `try/except`, хотя `grant_command` (7674-7708) специально обзавёлся таким `try/except` вокруг того же вызова с явным комментарием: глобальный `on_error` только пишет в логи, ничего не отвечает в чат, и без локальной обработки сбой (например при отправке уведомления целевому пользователю) выглядит как полное отсутствие реакции на нажатие кнопки.
