# Идеи по улучшению

## 2026-08-26

### UX/функциональность

- Нет отдельного сценария возврата после многодневного пропуска: `check_notifications` (bot.py:7264-7327) шлёт одинаковые ☀️/☕/🌙 уведомления независимо от того, пропустил человек 1 день или 3 недели; единственная "дни с X" логика в файле — вехи 3/7/14/30 дней от `created_at` для research-опросов (bot.py:7384-7391), а не от последней активности. Для СДВГ-аудитории со стыдом/all-or-nothing мышлением отдельное мягкое "с возвращением, стрик не важен, сделай только сегодня" сообщение по факту реального перерыва в активности снизило бы порог возврата.
- Есть только просветительский текст про лекарства ("медикаменты и психотерапия работают лучше вместе", bot.py:7015-7023), но нет самого напоминания принять лекарство — при этом инфраструктура времени/тумблеров для утра/дня/вечера (bot.py:7230-7280) уже позволяет добавить ещё один такой слот почти без новой архитектуры.
- Разбивка большой задачи на шаги — только в статье про навык дня (bot.py:100-105) и в подсказке "обратись к ИИ и опиши задачу" внутри мидей-техник (bot.py:6619-6643), но экран ввода задачи `_offer_task_input` (bot.py:4487-4502) не предлагает кнопку "🔧 Разбей эту задачу", которая передала бы уже введённый текст коучу напрямую — сейчас человеку с параличом инициации нужно самому заново печатать задачу в коуче.
- Нет калибровки "сколько думал — сколько заняло на самом деле": навык таймера прямо объясняет, что у СДВГ-мозга слабое внутреннее чувство времени (bot.py:127), но `go_focus`/`focus_start_callback` (bot.py:5530-5638) только дают выбрать длительность, не спрашивая прогноз "сколько думаешь это займёт?" до старта и не показывая потом "думал(а) 25, ушло 52".
- Бадди/body doubling — это просто шаблон текста для копипаста в другой чат (`buddy_menu`/`buddy_set`/`buddy_ping`, bot.py:6386-6433): бадди не является пользователем бота, не получает уведомление о старте сессии, нет общего таймера. Функция опирается ровно на тот же "нужно вручную инициировать" барьер, который и создаёт проблему для инициации задач у СДВГ.
- Режим "мало сил" доступен только задним числом и только утром: вся ветка низкой энергии (`morning_start` bot.py:1924-2032, `morning_notification` bot.py:6768-6787) включается по вчерашней вечерней оценке `e_energy in (1,2)` (вечерний ритуал bot.py:2813-3074) — нет пункта меню или дневной точки входа "сегодня плохой день, сократи всё сейчас", если человек проснулся не в форме или сломался посреди дня, хотя вчера вечером оценил себя нормально.

### Архитектура/структура

- Весь бот — один файл на 7977 строк / 309 функций: обработчики, 30 мест с `sqlite3.connect(DB_PATH)`, 260 вызовов `InlineKeyboardButton(`, промпты для AI и 7+ админ-команд (bot.py:7435-7844) перемешаны без границ модулей (`db.py`, `keyboards.py`, `ai.py`, `admin.py`).
- `weekly_report` (bot.py:6829-7157, ~330 строк) и `midday_callback` (bot.py:6499-6760, ~260 строк) в одной функции совмещают запрос к БД, вычисление бизнес-правил, сборку промпта для Anthropic и рендер сообщения/клавиатуры — нет разделения "посчитать данные отчёта" и "отрисовать отчёт".
- `handle_text` (bot.py:5228-5529, ~300 строк) — монолитный роутер свободного текста, разветвляющийся по десяткам `awaiting_*`-состояний (163 вхождения `awaiting_` по файлу) вместо таблицы диспетчеризации или отдельных обработчиков на состояние.
- `check_notifications` (bot.py:7198-7422, ~225 строк) — единственная per-minute джоба APScheduler (`scheduler.add_job` вызывается один раз на весь файл), которая инлайново обрабатывает утро/день/вечер/+2ч/недельный отчёт/понедельник для каждого пользователя в одном цикле; сложность этой функции уже приводила к реальным багам, задокументированным её же комментариями ("16-й чекап" и т.п.).
- Повторяющийся SQL-бойлерплейт: `sqlite3.connect(DB_PATH)` встречается 30 раз, `conn.commit()` — 15, `conn.close()` — 33 — почти идентичные блоки открытия/запроса/коммита/закрытия скопированы под каждый запрос вместо общего хелпера/контекст-менеджера соединения (факторизованы только `get_user`/`update_user`, bot.py:567,593).
- 5 мест вызова Anthropic API (около bot.py:3198, 3250, 3330, 3346, 3402) каждый раз заново создают `Anthropic(api_key=ANTHROPIC_KEY)` и собирают длинные промпты инлайн — нет общего клиента/модуля шаблонов промптов.
- `main()` (bot.py:7759-7977, ~220 строк) регистрирует все `CommandHandler`/`CallbackQueryHandler`, планировщик и старт приложения в одной функции — нет разделения на `setup_handlers()`/`setup_scheduler()`.

### Техдолг

- Нет логирования: `import logging` в файле отсутствует, есть только 36 вызовов `print()` для диагностики — сбои в проде не видны без ручного захвата stdout.
- Нет тестов вообще: ни `test_*.py`, ни `tests/`, ни pytest/unittest — при 7977 строках и 309 функциях нет автоматической проверки корректности.
- `update_user()` (bot.py:597) строит SQL через f-строку для имени колонки: `f"UPDATE users SET {k}=? WHERE user_id=?"` — значения параметризованы, но имя колонки — нет; сейчас все вызовы идут с литеральными именами колонок в коде, но паттерн — потенциальная SQL-инъекция, если ключ когда-нибудь придёт из пользовательского словаря.
- Синхронный sqlite3 вызывается напрямую внутри `async def`-хендлеров во всех ~30 местах, `asyncio.to_thread`/`run_in_executor` почти не используется — любой диск-I/O блокирует единственный event loop, замедляя всех одновременных пользователей.
- Модульные мутируемые глобальные переменные (`_morning_conv`/`_evening_conv` bot.py:70-71, `_skill_animation_file_ids` bot.py:204, `_seen_update_ids` bot.py:6297, `_last_heartbeat` bot.py:7420) держат состояние в процессе — предполагают единственный процесс/воркер, при масштабировании на несколько инстансов приведут к рассинхрону между пользователями.
- 71+ мест с `except Exception` (включая голые `except: return ""`) молча проглатывают все ошибки без логирования, скрывая первопричину сбоев AI-вызовов и работы с БД.
- Нет ограничений на длину/валидацию пользовательского свободного текста — он без проверок пишется в БД и подставляется в промпты Anthropic (5 мест вызова).
- `BOT_TOKEN = os.getenv("BOT_TOKEN", "YOUR_BOT_TOKEN")` и `NOTIFY_USER_ID = int(os.getenv("NOTIFY_USER_ID", "0"))` (bot.py:24,27) молча падают на плейсхолдер/ноль вместо явного отказа при отсутствии переменных окружения — деплой без нужных env-переменных не упадёт сразу, а тихо сломается по функциональности позже.
