# Идеи по улучшению

## 2026-08-26

### UX/функциональность

- Нет отдельного сценария возврата после многодневного пропуска: `check_notifications` (bot.py:7353-7577) шлёт одинаковые ☀️/☕/🌙 уведомления независимо от того, пропустил человек 1 день или 3 недели; единственная "дни с X" логика в файле — вехи 3/7/14/30 дней от `created_at` для research-опросов, а не от последней активности. Для СДВГ-аудитории со стыдом/all-or-nothing мышлением отдельное мягкое "с возвращением, стрик не важен, сделай только сегодня" сообщение по факту реального перерыва в активности снизило бы порог возврата.
- Есть только просветительский текст про лекарства ("медикаменты и психотерапия работают лучше вместе", bot.py:7174), но нет самого напоминания принять лекарство — при этом инфраструктура времени/тумблеров для утра/дня/вечера уже позволяет добавить ещё один такой слот почти без новой архитектуры.
- Разбивка большой задачи на шаги — только в статье про навык дня "Первый неподавляющий шаг" (bot.py:101) и в подсказке "обратись к ИИ и опиши задачу" внутри мидей-техник (`mid_nostart`/`mid_scary`, bot.py:6774-6797), но экран ввода задачи `_offer_task_input` (bot.py:4583-4599) не предлагает кнопку "🔧 Разбей эту задачу", которая передала бы уже введённый текст коучу напрямую — сейчас человеку с параличом инициации нужно самому заново печатать задачу в коуче.
- Нет калибровки "сколько думал — сколько заняло на самом деле": навык таймера прямо объясняет, что у СДВГ-мозга слабое внутреннее чувство времени (bot.py:127), но `go_focus`/`focus_start_callback` (bot.py:5685-5741) только дают выбрать длительность, не спрашивая прогноз "сколько думаешь это займёт?" до старта и не показывая потом "думал(а) 25, ушло 52".
- Бадди/body doubling — это просто шаблон текста для копипаста в другой чат (`buddy_menu`/`buddy_set`/`buddy_ping`, bot.py:6541-6575): бадди не является пользователем бота, не получает уведомление о старте сессии, нет общего таймера. Функция опирается ровно на тот же "нужно вручную инициировать" барьер, который и создаёт проблему для инициации задач у СДВГ.
- Режим "мало сил" доступен только задним числом и только утром: вся ветка низкой энергии (`morning_start`, `morning_notification`) включается по вчерашней вечерней оценке энергии из вечернего ритуала — нет пункта меню или дневной точки входа "сегодня плохой день, сократи всё сейчас", если человек проснулся не в форме или сломался посреди дня, хотя вчера вечером оценил себя нормально.
- Новая постановка задачи свободным текстом (`classify_free_text` intent `set_task`, `handle_set_task_intent`, bot.py:5174-5192) работает только для задач НА СЕГОДНЯ (слоты A/B1-C3). Точно такая же формулировка вечером про план на завтра ("поставь на завтра задачу — созвониться с врачом") по-прежнему требует пройти пошаговый `evening_plan_kb` — тот же барьер "заново вручную инициировать через кнопки", который эта фича как раз должна была снять для сегодняшних задач.
- «🆕 Что нового» (`show_whats_new`, bot.py:6467-6479) — экран есть, но найти его можно только зайдя во вкладку меню «⚙️ Настройки»; на самих вкладках/в главном меню нет никакого индикатора "есть непрочитанное" (бейджа/точки), так что пользователь, который не заглядывает в настройки специально, никогда не узнает о новых фичах, если сам не включил анонсы (`notify_updates`, по умолчанию выключены).

### Архитектура/структура

- Весь бот — один файл на 8133 строки / ~310 функций: обработчики, ~30 мест с `sqlite3.connect(DB_PATH)`, ~260 вызовов `InlineKeyboardButton(`, промпты для AI и 7+ админ-команд перемешаны без границ модулей (`db.py`, `keyboards.py`, `ai.py`, `admin.py`).
- `weekly_report` (bot.py:6984-7312, ~330 строк) и `midday_callback` (bot.py:6654-6915, ~260 строк) в одной функции совмещают запрос к БД, вычисление бизнес-правил, сборку промпта для Anthropic и рендер сообщения/клавиатуры — нет разделения "посчитать данные отчёта" и "отрисовать отчёт".
- `handle_text` (bot.py:5381-5684, ~300 строк) — монолитный роутер свободного текста, разветвляющийся по десяткам `awaiting_*`-состояний вместо таблицы диспетчеризации или отдельных обработчиков на состояние.
- `check_notifications` (bot.py:7353-7577, ~225 строк) — единственная per-minute джоба APScheduler (`scheduler.add_job`, bot.py:8121, вызывается один раз на весь файл), которая инлайново обрабатывает утро/день/вечер/+2ч/недельный отчёт/понедельник для каждого пользователя в одном цикле; сложность этой функции уже приводила к реальным багам, задокументированным её же комментариями ("16-й чекап" и т.п.).
- Повторяющийся SQL-бойлерплейт: `sqlite3.connect(DB_PATH)` открывается отдельно в каждой из ~30 DB-функций — почти идентичные блоки открытия/запроса/коммита/закрытия скопированы под каждый запрос вместо общего хелпера/контекст-менеджера соединения (факторизованы только `get_user`/`update_user`, bot.py:569,595).
- Несколько мест вызова Anthropic API каждый раз заново создают `Anthropic(api_key=ANTHROPIC_KEY)` и собирают длинные промпты инлайн — нет общего клиента/модуля шаблонов промптов.
- `main()` (bot.py:7914-8133, ~220 строк) регистрирует все `CommandHandler`/`CallbackQueryHandler`, планировщик и старт приложения в одной функции — нет разделения на `setup_handlers()`/`setup_scheduler()`.
- `go_tab` (bot.py:5670-5684) заново пишет тот же `try: q.message.edit_text(...) / except: q.message.reply_text(...)`, что уже вынесен в общий хелпер `_edit_or_send` (bot.py:1363-1373) и используется остальными ~15 местами редактирования экрана на месте — единственный оставшийся вызов, который не переиспользует общую функцию, из-за чего любой будущий фикс/доработка `_edit_or_send` (например, обработка `Message is not modified`) молча не затронет именно переключение вкладок меню, если про эту копию забудут.

### Техдолг

- Нет логирования: `import logging` в файле отсутствует, диагностика идёт только через `print()` — сбои в проде не видны без ручного захвата stdout.
- Нет тестов в репозитории: несмотря на то, что сообщения последних коммитов (например #141) описывают прогон `test_task_management_improvements.py`, самого файла с тестами в дереве репозитория нет — при 8133 строках и ~310 функциях нет ни одной автоматической проверки, которая реально хранится и гоняется в CI.
- `update_user()` (bot.py:599) строит SQL через f-строку для имени колонки: `f"UPDATE users SET {k}=? WHERE user_id=?"` — значения параметризованы, но имя колонки — нет; сейчас все вызовы идут с литеральными именами колонок в коде, но паттерн — потенциальная SQL-инъекция, если ключ когда-нибудь придёт из пользовательского словаря.
- Синхронный sqlite3 вызывается напрямую внутри `async def`-хендлеров во всех DB-функциях, `asyncio.to_thread`/`run_in_executor` почти не используется — любой диск-I/O блокирует единственный event loop, замедляя всех одновременных пользователей.
- Модульные мутируемые глобальные переменные (`_morning_conv`/`_evening_conv` bot.py:70-71, `_skill_animation_file_ids` bot.py:204, `_seen_update_ids` bot.py:6452, `_last_heartbeat` bot.py:7356,7575) держат состояние в процессе — предполагают единственный процесс/воркер, при масштабировании на несколько инстансов приведут к рассинхрону между пользователями.
- Много мест с `except Exception` (в т.ч. голые `except: pass`/`except: return ""`) молча проглатывают все ошибки без логирования, скрывая первопричину сбоев AI-вызовов и работы с БД.
- Нет ограничений на длину/валидацию пользовательского свободного текста — он без проверок пишется в БД и подставляется в промпты Anthropic.
- `BOT_TOKEN = os.getenv("BOT_TOKEN", "YOUR_BOT_TOKEN")` и `NOTIFY_USER_ID = int(os.getenv("NOTIFY_USER_ID", "0"))` (bot.py:24,27) молча падают на плейсхолдер/ноль вместо явного отказа при отсутствии переменных окружения — деплой без нужных env-переменных не упадёт сразу, а тихо сломается по функциональности позже.
- `CHANGELOG`/`_whats_new_text` (bot.py:85-127) — список анонсов, который, по замыслу самого куратора в комментарии, будет пополняться вручную при каждой значимой фиче и никогда не чистится. `_whats_new_text(limit=5)` просто конкатенирует title+text первых пяти записей без проверки суммарной длины — лимит Telegram на текст сообщения 4096 символов. Пока записей четыре и они короткие, запас есть, но нет ни теста, ни рантайм-проверки, которая поймает превышение лимита, когда список отредактируют/пополнят через полгода — сообщение "🆕 Что нового" (и `/broadcast latest`) в этот момент молча упадёт с ошибкой Telegram API вместо отправки.
