## 2026-08-26

### UX/функциональность

- Нет отдельного сценария возврата после многодневного пропуска: `check_notifications` (bot.py:7353-7577) шлёт одинаковые ☀️/☕/🌙 уведомления независимо от того, пропустил человек 1 день или 3 недели; единственная "дни с X" логика в файле — вехи 3/7/14/30 дней от `created_at` для research-опросов, а не от последней активности. Для СДВГ-аудитории со стыдом/all-or-nothing мышлением отдельное мягкое "с возвращением, стрик не важен, сделай только сегодня" сообщение по факту реального перерыва в активности снизило бы порог возврата.
- Есть только просветительский текст про лекарства ("медикаменты и психотерапия работают лучше вместе", bot.py:7174), но нет самого напоминания принять лекарство — при этом инфраструктура времени/тумблеров для утра/дня/вечера уже позволяет добавить ещё один такой слот почти без новой архитектуры.
- Разбивка большой задачи на шаги — только в статье про навык дня "Первый неподавляющий шаг" (bot.py:101) и в подсказке "обратись к ИИ и опиши задачу" внутри мидей-техник (`mid_nostart`/`mid_scary`, bot.py:6774-6797), но экран ввода задачи `_offer_task_input` (bot.py:4583-4599) не предлагает кнопку "🔧 Разбей эту задачу", которая передала бы уже введённый текст коучу напрямую — сейчас человеку с параличом инициации нужно самому заново печатать задачу в коуче.
- Нет калибровки "сколько думал — сколько заняло на самом деле": навык таймера прямо объясняет, что у СДВГ-мозга слабое внутреннее чувство времени (bot.py:127), но `go_focus`/`focus_start_callback` (bot.py:5685-5741) только дают выбрать длительность, не спрашивая прогноз "сколько думаешь это займёт?" до старта и не показывая потом "думал(а) 25, ушло 52".
- Бадди/body doubling — это просто шаблон текста для копипаста в другой чат (`buddy_menu`/`buddy_set`/`buddy_ping`, bot.py:6541-6575): бадди не является пользователем бота, не получает уведомление о старте сессии, нет общего таймера. Функция опирается ровно на тот же "нужно вручную инициировать" барьер, который и создаёт проблему для инициации задач у СДВГ.
- Режим "мало сил" доступен только задним числом и только утром: вся ветка низкой энергии (`morning_start`, `morning_notification`) включается по вчерашней вечерней оценке энергии из вечернего ритуала — нет пункта меню или дневной точки входа "сегодня плохой день, сократи всё сейчас", если человек проснулся не в форме или сломался посреди дня, хотя вчера вечером оценил себя нормально.
- Новая постановка задачи свободным текстом (`classify_free_text` intent `set_task`, `handle_set_task_intent`, bot.py:5174-5192) работает только для задач НА СЕГОДНЯ (слоты A/B1-C3). Точно такая же формулировка вечером про план на завтра ("поставь на завтра задачу — созвониться с врачом") по-прежнему требует пройти пошаговый `evening_plan_kb` — тот же барьер "заново вручную инициировать через кнопки", который эта фича как раз должна была снять для сегодняшних задач.
- «🆕 Что нового» (`show_whats_new`, bot.py:6467-6479) — экран есть, но найти его можно только зайдя во вкладку меню «⚙️ Настройки»; на самих вкладках/в главном меню нет никакого индикатора "есть непрочитанное" (бейджа/точки), так что пользователь, который не заглядывает в настройки специально, никогда не узнает о новых фичах, если сам не включил анонсы (`notify_updates`, по умолчанию выключены).

### Архитектура/структура

- Весь бот — один файл на 8133 строки / ~310 функций: обработчики, ~30 мест с `sqlite3.connect(DB_PATH)`, ~260 вызовов `InlineKeyboardButton(`, промпты для AI и 7+ админ-команд перемешаны без границ модулей (`db.py`, `keyboards.py`, `ai.py`, `admin.py`).
- `weekly_report` (bot.py:6984-7312, ~330 строк) и `midday_callback` (bot.py:6654-6915, ~260 строк) в одной функции совмещают запрос к БД, вычисление бизнес-правил, сборку промпта для Anthropic и рендер сообщения/клавиатуры — нет разделения "посчитать данные отчёта" и "отрисовать отчёт".
- `handle_text` (bot.py:5381-5684, ~300 строк) — монолитный роутер свободного текста, разветвляющийся по десяткам `awaiting_*`-состояний вместо таблицы диспетчеризации или отдельных обработчиков на состояние.
- `check_notifications` (bot.py:7353-7577, ~225 строк) — единственная per-minute джоба APScheduler (`scheduler.add_job`, bot.py:8121, вызывается один раз на весь файл), которая инлайново обрабатывает утро/день/вечер/+2ч/недельный отчёт/понедельник для каждого пользователя в одном цикле; сложность этой функции уже приводила к реальным багам, задокументированным её же комментариями ("16-й чекап" и т.п.).
- Повторяющийся SQL-бойлерплейт: `sqlite3.connect(DB_PATH)` открывается отдельно в каждой из ~30 DB-функций — почти идентичные блоки открытия/запроса/коммита/закрытия скопированы под каждый запрос вместо общего хелпера/контекст-менеджера соединения (факторизованы только `get_user`/`update_user`, bot.py:569,595).
- Несколько мест вызова Anthropic API каждый раз заново создают `Anthropic(api_key=ANTHROPIC_KEY)` и собирают длинные промпты инлайн — нет общего клиента/модуля шаблонов промптов.
- `main()` (bot.py:7914-8133, ~220 строк) регистрирует все `CommandHandler`/`CallbackQueryHandler`, планировщик и старт приложения в одной функции — нет разделения на `setup_handlers()`/`setup_scheduler()`.
- `go_tab` (bot.py:5670-5684) заново пишет тот же `try: q.message.edit_text(...) / except: q.message.reply_text(...)`, что уже вынесен в общий хелпер `_edit_or_send` (bot.py:1363-1373) и используется остальными ~15 местами редактирования экрана на месте — единственный оставшийся вызов, который не переиспользует общую функцию, из-за чего любой будущий фикс/доработка `_edit_or_send` (например, обработка `Message is not modified`) молча не затронет именно переключение вкладок меню, если про эту копию забудут.

### Техдолг

- Нет логирования: `import logging` в файле отсутствует, диагностика идёт только через `print()` — сбои в проде не видны без ручного захвата stdout.
- Нет тестов в репозитории: несмотря на то, что сообщения последних коммитов (например #141) описывают прогон `test_task_management_improvements.py`, самого файла с тестами в дереве репозитория нет — при 8133 строках и ~310 функциях нет ни одной автоматической проверки, которая реально хранится и гоняется в CI.
- `update_user()` (bot.py:599) строит SQL через f-строку для имени колонки: `f"UPDATE users SET {k}=? WHERE user_id=?"` — значения параметризованы, но имя колонки — нет; сейчас все вызовы идут с литеральными именами колонок в коде, но паттерн — потенциальная SQL-инъекция, если ключ когда-нибудь придёт из пользовательского словаря.
- Синхронный sqlite3 вызывается напрямую внутри `async def`-хендлеров во всех DB-функциях, `asyncio.to_thread`/`run_in_executor` почти не используется — любой диск-I/O блокирует единственный event loop, замедляя всех одновременных пользователей.
- Модульные мутируемые глобальные переменные (`_morning_conv`/`_evening_conv` bot.py:70-71, `_skill_animation_file_ids` bot.py:204, `_seen_update_ids` bot.py:6452, `_last_heartbeat` bot.py:7356,7575) держат состояние в процессе — предполагают единственный процесс/воркер, при масштабировании на несколько инстансов приведут к рассинхрону между пользователями.
- Много мест с `except Exception` (в т.ч. голые `except: pass`/`except: return ""`) молча проглатывают все ошибки без логирования, скрывая первопричину сбоев AI-вызовов и работы с БД.
- Нет ограничений на длину/валидацию пользовательского свободного текста — он без проверок пишется в БД и подставляется в промпты Anthropic.
- `BOT_TOKEN = os.getenv("BOT_TOKEN", "YOUR_BOT_TOKEN")` и `NOTIFY_USER_ID = int(os.getenv("NOTIFY_USER_ID", "0"))` (bot.py:24,27) молча падают на плейсхолдер/ноль вместо явного отказа при отсутствии переменных окружения — деплой без нужных env-переменных не упадёт сразу, а тихо сломается по функциональности позже.
- `CHANGELOG`/`_whats_new_text` (bot.py:85-127) — список анонсов, который, по замыслу самого куратора в комментарии, будет пополняться вручную при каждой значимой фиче и никогда не чистится. `_whats_new_text(limit=5)` просто конкатенирует title+text первых пяти записей без проверки суммарной длины — лимит Telegram на текст сообщения 4096 символов. Пока записей четыре и они короткие, запас есть, но нет ни теста, ни рантайм-проверки, которая поймает превышение лимита, когда список отредактируют/пополнят через полгода — сообщение "🆕 Что нового" (и `/broadcast latest`) в этот момент молча упадёт с ошибкой Telegram API вместо отправки.

### Архитектура/структура

- Порядка 1500+ строк чистого текстового контента (`SKILLS` bot.py:129+, `CHANGELOG` bot.py:85+, `ABOUT_SECTIONS` bot.py:7135+, `GUIDE_SECTIONS` bot.py:8252+) перемешаны в одном файле с бизнес-логикой — стоит вынести в отдельный `content.py`. Правки текста (судя по частоте записей в `CHANGELOG` — обычное дело в этом проекте) сейчас требуют трогать тот же файл, что и логику хендлеров, размывая диффы и повышая риск конфликтов при параллельной работе.
- "Одно живое сообщение на канал" реализовано параллельно четырьмя разными механизмами хранения message_id: ключи `ctx.user_data["{track_key}_msg_id"/"_chat_id"]` для `_render_tracked`/`_render_step_msg`, таблица `notif_msg_ids` для `send_tracked_notification`, отдельная таблица `ritual_msg_ids` для `_track_ritual_msg`, и таблица `scheduled_deletions` для отложенного самоудаления по тишине. Все четыре решают ту же задачу "запомнить/заменить/стереть по таймауту одно сообщение", но независимым кодом — унификация в один модуль убрала бы уже случившееся расхождение в поведении (см. баги про `focus_timer` TTL и анимацию маячка выше).
- `classify_free_text` (bot.py:4011-4113) и `parse_reminder_request` (bot.py:3956-4010) почти дословно дублируют друг друга: тот же системный промпт с разбором даты/времени/повтора, тот же `re.search(r"\{.*\}")`-парсинг JSON-ответа, тот же паттерн создания клиента Anthropic — стоит выделить общий разбор времени/повтора в одну функцию, переиспользуемую в обеих.

### Техдолг

- Все вызовы Anthropic SDK (`parse_reminder_request`, `classify_free_text`, `ai_morning_boost`, `ai_day_analysis`, `send_coach`) синхронные и выполняются без `asyncio.to_thread`/`run_in_executor` внутри `async def`-хендлеров — сетевой запрос к Claude блокирует единственный event loop бота целиком (см. баг выше). Это не только тормозит одновременных пользователей, но и напрямую бьёт по надёжности `check_notifications` — единственной раз-в-минуту джобе, которая шлёт все утренние/дневные/вечерние напоминания и маячки.
- `check_notifications` (bot.py:8508+) перебирает всех пользователей строго последовательно (`for user in users: ... await ...`) внутри одного тика раз в минуту, без `asyncio.gather`/семафора — при росте базы пользователей, а тем более при блокирующих Anthropic-вызовах у одного из них (см. пункт выше), тик рискует не уложиться в 60 секунд и задержать уведомления всем, кто идёт следующим в списке в этом же тике.

### UX/функциональность

- Быстрые кнопки коуча (`COACH_PROMPTS`, bot.py:4300-4306) все заточены под старт/прокрастинацию задачи ("не могу начать", "отвлёкся", "что дальше" и т.п.) — нет ни одной под стыд/реакцию на срыв или чужую реакцию, хотя онбординг отдельно собирает `self_esteem`/`self_talk`/`unfinished_shame` как отдельную группу трудностей, а не просто "не могу начать".

### Архитектура/структура

- Порядка 18-20 пар хендлеров шагов ритуала (`got_writing`/`skip_m_writing`, `got_gratitude`/`skip_m_gratitude`, `got_child`/`skip_m_child` в утре; `got_e_ach`, `got_e_praise`, `got_e_highlights`, `got_e_a`, `got_e_b1`, `got_e_b2`, `got_e_c1/c2/c3` в вечере, bot.py:2751-2765, 3474-3737) отличаются друг от друга только именем ключа в `ctx.user_data` и следующим шагом — по сути одна и та же 5-8-строчная форма, скопированная вручную ~18-20 раз вместо табличного генератора `(key, next_step) -> handler`.

### Техдолг

- Нигде в файле нет обработки ситуации "пользователь заблокировал бота" (нет ни одного места, реагирующего на `Forbidden`/blocked): при оттоке пользователей `check_notifications`/рассылки просто падают в общий `except Exception`, печатают в лог и повторяют попытку на каждом следующем тике бесконечно — нет логики проставить таким пользователям `notif_enabled=0`, что усугубляет уже отмеченный риск не уложиться в 60-секундный тик по мере роста числа заблокировавших.
- Нет вообще никакого бэкапа/экспорта единственной SQLite-базы — `init_db()` включает WAL-режим для защиты от блокировок при параллельной записи, но во всём файле нет ни одной команды дампа БД или админ-команды для бэкапа: потеря/повреждение диска на хостинге означает безвозвратную потерю всех дневников, стриков и промокодов.

- Вечерний чек-лист самопомощи `SELFCARE_ITEMS` (13 пунктов, bot.py:3563-3577: зарядка, холодная вода, бумажка гениальных мыслей, готовность и полуулыбка и т.д.) заметно шире набора техник, доступных дневному маячку — `BEACON_TECHNIQUE_TYPES` (всего 4: stop/breathing/grounding/anchor, bot.py:5051-5056). Вечером бот спрашивает про 13 разных практик самопомощи, но днём маячок физически не может напомнить про большинство из них — просто нет ключа в ротации.
- Экран сработавшего напоминания (`send_due_reminders`, bot.py:6308-6333) даёт только уведомление с текстом — нет кнопки быстрого "⏰ Ещё через 10 мин" (снуза), хотя для аудитории с СДВГ это одна из самых частых потребностей именно у напоминаний, не только у фокус-таймера (для которого снуз уже частично решается через продление раунда).
- 📥 Список дел (`task_pool_kb`, bot.py:6009-6015) позволяет только добавить или удалить пункт — нет "✏️ изменить текст" уже существующего дела, приходится удалять и печатать заново, что для аудитории с исполнительной дисфункцией — лишний барьер именно там, где хотелось бы наименьшего трения.
- `weekly_report` (bot.py:8319+) собирает и хранит `focus_minutes_today` посуточно (используется в `send_focus_end`), а комментарий в самой функции (около bot.py:8387) прямо говорит "Фокус-минуты берём из DB... простая версия: показываем что есть" — но итоговый текст отчёта эти данные так и не использует. Еженедельная агрегация фокус-минут задумана, но не дописана — недостающий один шаг у уже собираемых данных.

### Архитектура/структура

- `clear_awaiting_flags(ctx, update=None)` (bot.py:6435-6478) — одна функция с двумя разными по последствиям режимами поведения, различаемыми только наличием необязательного параметра `update`: без него — просто чистит флаги, с ним — ещё и обрывает активный `ConversationHandler`. Именно эта неявная развилка уже стала причиной минимум двух похожих багов на разных экранах (см. `use_yesterday_plan_callback`, где её обошли, и `quick_toggle_beacon`/`quick_toggle_skill`, где не обошли — BUGS.md 2026-08-29). Стоит завести два явно по-разному названных хелпера (например `clear_awaiting_flags` только для флагов и `cancel_active_ritual` для отмены диалога), чтобы автор нового хендлера на персистентной кнопке не выбирал сигнатуру наугад.
- Онбординг (`got_name → got_gender → onboard_trained_yes/no → onboard_guide_section/done → toggle_problem/problem_group_next/problems_done → onboard_explain_* → onboard_done → onboard_notif_on/skip`, bot.py:1726-2176, ~15 функций) — отдельный, такой же по объёму копипаст-блок, как уже отмеченные пары шагов утреннего/вечернего ритуала: в каждой функции вручную повторяется тройка `await q.answer()` / `_onboard_clear_prev(...)` / `_onboard_track(...)`. Стоило бы прогнать через тот же паттерн "шаг-раннер", что уже применяется для ритуала.
- Утренний и вечерний ритуалы дублируют не только пары `got_*`/`skip_*`-хендлеров (уже отмечено ранее), но и весь движок резюме/чекпоинта целиком: `RESUME_FIELDS`+`advance_morning`+`checkpoint_morning_progress` (bot.py:2830-3104) и `RESUME_FIELDS_EVENING`+`advance_evening`+`checkpoint_evening_progress` (bot.py:3789-3894) — независимо реализованная логика обработки disabled-полей, дат и "все шаги пройдены, а флаг в БД ещё нет". Именно рассинхрон между этими двумя копиями уже приводил к разному поведению (см. баг потери данных в `morning_start` — BUGS.md 2026-08-29). Стоит вынести в один параметризуемый степпер.
- `_task_checkbox_rows` (bot.py:5420-5435) в своём же докстринге объявлена единой логикой построения чекбоксов задач, "чтобы не рассинхронизировать" `midday_kb` и `_tasks_text_and_kb" — но `_tasks_text_and_kb` её не вызывает, а копирует ту же логику инлайн (bot.py:5466-5477). Рассинхронизация, от которой функция должна защищать по замыслу, ничем архитектурно не предотвращена — только дисциплиной разработчика.
- Паттерн `if not await _edit_tracked_msg(ctx, "<channel>", text, ...): await message.reply_text(...)` буквально повторён минимум 13 раз (например bot.py:5798-5799, 5814-5815, 5979-5980, 6527-6528, 6546-6547, 6669-6670, 6696-6697, 6728-6729, 6751-6752) — просится в общий хелпер вида `_reply_or_edit_tracked(ctx, message, track_key, text, **kwargs)`.

### Техдолг

- `_sync_tz_lookup`-путь определения города/таймзоны (bot.py:1046-1059) делает `from geopy.geocoders import Nominatim` и `from timezonefinder import TimezoneFinder` внутри функции, в одном общем `try/except Exception` вместе с самим геокодингом. Если эти опциональные зависимости не установлены в проде (сломался деплой/requirements.txt), `ImportError` тихо превращается в тот же самый ответ "не смог определить город автоматически", что и для реального нераспознанного города — вся функция может быть системно сломана для абсолютно всех пользователей, а выглядеть это будет как обычный единичный edge-case.
- `dedupe_updates` (bot.py:7748-7761, group=-3, вызывается на каждый входящий апдейт без исключения) на каждый вызов делает `for old_id, ts in list(_seen_update_ids.items())` для очистки устаревших записей — O(n) полное сканирование и копирование словаря при каждом сообщении/колбэке, вместо периодического sweep отдельным cron-джобом (как уже сделано для `sweep_scheduled_deletions`). При росте активной аудитории и трафика — лишняя постоянно растущая нагрузка на каждый апдейт.
